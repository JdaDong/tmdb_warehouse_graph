# 01 · 总体架构设计

## 1.1 目标与非目标

**目标**

- 以 TMDB 为数据源，构建可生产运行的数据平台：离线数仓、实时数仓、OLAP 数据治理、图数据库。
- 全链路幂等、可重跑：任意一天的数据可以安全重算，结果与首次运行一致。
- 所有组件本地可一键启动；无 TMDB API Key 时用内置 Mock 跑通全链路。
- 治理不是"附加功能"，而是围绕 OLAP 引擎展开的一等公民：元数据血缘、数据质量、生命周期、权限、指标口径。

**非目标**

- 不做 BI 可视化前端（只提供 ADS 表与查询接口）。
- 不做多租户与细粒度行级权限（提供到"角色 × 库表"粒度）。
- 不追求超大规模：单集群形态面向 TB 级数据量与每日百万级增量。

## 1.2 技术选型与理由

| 层次 | 选型 | 选型理由 | 被否决的方案 |
|---|---|---|---|
| 采集 | Java 17 + 对象存储 | 需要精确控制限流 / 重试 / 断点续传；与下游 Spark / Flink 同一语言栈 | Python 采集（与计算栈割裂，排障要跨两套运行时） |
| 离线计算 | Spark 3.5 + Iceberg | 批式分层建模成熟；Iceberg 提供 ACID 与快照回滚 | Hive 表（无 ACID、无时间旅行） |
| 实时计算 | Flink 1.18 | 事件时间语义、Exactly-Once、状态管理完备 | Spark Streaming（微批，延迟与语义都弱于 Flink） |
| 消息队列 | Kafka 3.7（KRaft） | 可重放是"实时不准、离线兜底"的前提 | Pulsar（生态与运维复杂度更高） |
| OLAP | ClickHouse 24.3 | 单表分析性能强，物化视图与 TTL/冷热分层成熟 | Doris / StarRocks（亦可，本项目选 CH 因其单机即可跑通且生态成熟） |
| 图数据库 | Neo4j 5.20 | Cypher 生态成熟，单机易跑，社区版功能足够 | NebulaGraph（分布式更强，但本地门槛高） |
| 湖仓存储 | MinIO（S3 协议） | 本地可跑，生产可无缝换 S3/OSS | HDFS（本地部署成本高） |
| 调度 | Airflow 2.9 | DAG 表达依赖清晰，社区成熟 | 自研调度（重复造轮子） |
| 元数据 | OpenMetadata | 开源、支持 ClickHouse 与 Kafka | DataHub（亦可，本项目选 OM） |
| 监控 | Prometheus + Grafana | 各组件原生暴露指标，告警规则统一 | 云监控（绑定厂商） |

## 1.4 数据流

**离线（T+1）**

1. 全量：每日 ID 导出文件 → 逐条详情 → 对象存储 `raw/{entity}/dt=...`（支持断点续传）。
2. 增量：changes 接口 + 水位线推进（14 天窗口切分，对应 TMDB 接口限制）。
3. Spark：ODS 解析 → DWD 清洗建模（维度 SCD2）→ DWS 汇总 → ADS 报表。
4. 写入 Iceberg 湖仓；同步到 ClickHouse（维度按窗口删除重写，事实按分区替换）。

**实时（分钟级）**

1. 热度榜单轮询 → Kafka `popularity` Topic。
2. Flink：解码 → 内容级去重 → 落 ODS 事件（离线兜底）→ 窗口聚合 → rt 库 → 飙升检测 → 告警。
3. 坏消息进 DLQ，不阻断主链路。

**图（每日）**

1. 从 ClickHouse 维度 / 桥接表读取 → Neo4j（MERGE 幂等装载）。
2. 图分析（度数中心性、合作网络、相似推荐等）结果回流 ClickHouse。

## 1.5 关键设计决策

### 决策 1：离线结果以湖仓为准，ClickHouse 是"查询副本"

湖仓（Iceberg）保存分层结果与快照，ClickHouse 只承担查询。好处：
- ClickHouse 表可以随时重建（从湖仓重灌），不必担心"表结构演进后历史数据无法回溯"；
- 口径调整可在湖仓上重算，再整体替换 ClickHouse 分区，切换是原子的。

### 决策 2：所有写入必须幂等

- 离线：维度全量覆盖、事实按 `dt` 分区覆盖；`load_time` 固定为业务日期零点，保证重跑得到相同值。
- 实时：ClickHouse 侧用 `ReplacingMergeTree`（ORDER BY 业务主键 + version 取事件时间）去重，
  因为 ClickHouse 不支持分布式事务，无法把 Flink 的 Exactly-Once 延伸到 Sink 端。
- 图：全部 `MERGE`，重复装载不产生重复节点。

### 决策 3：治理围绕 OLAP 引擎展开

治理的对象是 ClickHouse 里的表与字段：元数据快照、血缘、质量结果、生命周期执行记录
全部落在 `governance` 库，与业务数据同库管理、同样的 TTL 与冷热策略，避免"治理元数据自己失控"。

### 决策 4：实时不准，离线兜底

实时链路写入的每张表都有对应的离线重算路径：
- 事件级：`ods.ods_change_event` / `ods.ods_popularity_event` 保存原始事件（按 `event_id` 去重）；
- 汇总级：离线 DWS 按同一口径重算，与实时结果可对账。
这样即使 Flink 作业出错，也不会造成数据永久丢失或口径长期偏离。

### 决策 5：不可运行的代码不算交付

- 所有组件有 Docker Compose 定义，本地可一键启动；
- 没有 TMDB API Key 时用 WireMock（完整模拟限流、故障、分页、导出文件）；
- 单元测试用真实 Spark（local 模式）跑真实报文，不靠 mock 断言"调用过方法"；
- 需要 Docker 的测试单独用 `-Pit` profile，无 Docker 时自动跳过而不是失败。

## 1.6 模块划分

| 模块 | 职责 | 产物 |
|---|---|---|
| `tmdb-common` | 配置、模型、工具、对象存储、ClickHouse 客户端 | 库（不产出 jar） |
| `tmdb-ingestion` | TMDB 采集：全量 / 增量 / 热度轮询 | `ingestion.jar` |
| `tmdb-offline` | Spark 离线分层 + 湖仓写入 + ClickHouse 同步 | `offline.jar` |
| `tmdb-realtime` | Flink 实时作业 | `realtime.jar` |
| `tmdb-graph` | Neo4j 装载与分析 | `graph.jar` |
| `tmdb-governance` | 迁移 / 质量 / 血缘 / 生命周期 / 权限 / 指标 | `governance.jar` |
